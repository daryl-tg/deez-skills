# OM Chat feature map

One file per user-facing feature. Each names the routes that reach it, the
handles that drive it, and the traps that have already cost someone a run.

This map is the repo's maintained verification source. **A proof that drives
one convenient entry point is incomplete when the file lists others.** If you
verify channel navigation from the sidebar and the file also lists the mobile
tab bar and the topic breadcrumb, either drive those too or say in the manifest
which you skipped and why.

Each file has the same four sections, in order:

1. **Sub-features** — what actually has to work, itemised.
2. **How to get to it (user POV)** — what a person does, in their words.
3. **Driving it with control-om-chat** — the routes and commands, with real
   accessible names from this repo.
4. **Gotchas** — what breaks, what lies, what the fixture cannot prove.

## Reaching the lane

Every snippet in these files opens its harness through the wrapper:

```bash
cd /Users/dboon/gitlab/openmarket-chat
export OM_CHAT_LANE_PORT=<your assigned 18097-18197 port>   # control-om-chat doctor
control-om-chat up
agent-browser open "$(control-om-chat url '<path>?<query>')"
```

`control-om-chat url` builds the origin from `OM_CHAT_LANE_PORT`, so nothing
here hardcodes a port. That matters more than it looks: lanes are assigned per
run, several worktrees drive at once, and a literal port copied out of a doc
lands you on **another run's app** — where everything renders and every frame
is evidence of the wrong tree.

### Stub the people directory first (required at `82390825`)

Since `431f630e`, `resolveCanonicalDisplayName` reads `session.people.held(...)`
(`packages/chat-ui/src/components/DisplayName.tsx`). Neither shell fixture stubs
`people`, so the autofill proxy answers with truthy `INERT`, `card.displayName`
becomes a function, and the `<Avatar>` subtree throws "Functions are not valid as
a React child". Every `shell-fixture.html` route on **both** hosts renders a
blank `#root`, as does `settings-fixture.html?host=server&page=moderation`.
`session.spaceMutes?.until(...)` has the same fault and would replace the composer
with the muted notice.

Until the fixtures stub them, start every browser session with an init script.
`autofill` tests `key in target`, so a non-enumerable `Object.prototype` property
is seen as a spelled-out session member, and no product file changes:

```bash
cat > "$SCRATCH/fixture-people-stub.js" <<'JS'
(() => {
  const define = (k, v) =>
    Object.defineProperty(Object.prototype, k, { value: v, configurable: true, writable: true, enumerable: false });
  define("people", {
    version: 0, generation: 0, subscribe: () => () => {}, held: () => null,
    cachedMembers: () => [], heldIn: () => [], byHandle: () => null, searched: () => null,
    search: () => () => {}, note: () => {}, noteMembers: () => {}, card: () => null,
    reconnected: () => {}, rolesChanged: () => {}, profileChanged: () => {}, dispose: () => {},
  });
  define("spaceMutes", { until: () => null, mute: async () => {}, unmute: async () => {} });
})();
JS
agent-browser --init-script "$SCRATCH/fixture-people-stub.js" open about:blank
agent-browser open "$(control-om-chat url 'tools/visual/shell-fixture.html?view=room&alerts=quiet')"
```

With it, `#ops` on both hosts shows 16 message rows and a working composer
(2026-11-09). Every recipe in this map assumes the stub on a shell route. The
same mechanism seeds states the fixtures cannot reach: return an ISO time from
`spaceMutes.until` for the muted composer, a **cached** `{status:"ready",people:[…]}`
from `people.searched` for server-wide `@` hits (a fresh object on every read makes
`useSyncExternalStore` loop), and `spacePermissionsVersion: () => 7` plus
`spaceActionAllowed: () => true` for the server-mute surfaces. Stay inside the
`autofill` fixtures; the standalone harnesses (agent centre, persona, away and
others) do not need it.

The stub carries every public `PeopleDirectory` member (`lib/people.ts:119`).
The first version lacked `heldIn`, and the Projects filters crash on it with
"session.people?.heldIn is not a function" (2026-11-09).

### Seed spelled-out keys with the session-capture shim

The `Object.prototype` trick only reaches keys the fixture leaves out. For a key
the fixture spells out (`openForward: noop`, `recoveryNudge: null`,
`forwardSource: null`, `roleCard: null`), wrap `window.Proxy` in an init script
so the `autofill` target is kept as `window.__om`, then assign over it and call
`__om.closeConfirm()` to repaint (it sets `confirmDialog = null` and calls the
fixture's `emit()`). The recipe is in [message-actions.md](message-actions.md)
(Forward), and it also drives the recovery nudge
([composer-and-sending.md](composer-and-sending.md)) and the topic handoff
([channel-and-topic-navigation.md](channel-and-topic-navigation.md)). It works
on both hosts (2026-11-09). [projects.md](projects.md) uses the prototype
trick with a `todos` store instead, because `todos` is not spelled out.

**`message=cozy` is sticky, and nothing unsets it.** It writes
`om.chat.messageDisplay` to `localStorage` and the fixture has no `else` branch
to clear it, so every later load in that browser session stays cozy — including
the load you meant to capture as the default. A before/after comparison run in
one session therefore shows no difference and looks like a dead parameter.
Clear the key before capturing a default frame:

```bash
agent-browser eval 'localStorage.removeItem("om.chat.messageDisplay")'
```

Cozy is visible as `msg-identity-cozy` on a `[data-message-row]`; the default is
`msg-identity-chassis mt-2` without it. (The settings fixture's `contrast=high`
does clear itself — that asymmetry is why only this one bites.)

`?alerts=quiet` is worth reaching for by default: without it the fixture fires
an app-wide alert strip that shifts every surface below it down. The board
renders the **two** rows actually seeded (`af-store-5xx`, `af-relay-latency`).
The channel-header beacon that used to read `Alerts: 3 feeds are ringing` has
not rendered since `dc6a9a47` (see [alerts.md](alerts.md)), so do not look for
it or caption a frame with its count. Those two are seed **ids**, not rendered text, so grepping a snapshot for
`af-store-5xx` finds nothing and looks like the board failed to render. What
you will find is `store-5xx · check pods` — and that string comes from the
**strip**, which renders `name · actionLine` and is layered above the content,
not from the board's own row, which shows the bare name. Both are on screen
under `?alerts=board`; say which one a caption means.

## Who adds to this map

Two paths, and the first is the cheap one.

**A feature run**, when its terminal gate drives a surface no file covers. That
is the moment the handles are known and the proof is fresh, so writing the file
costs almost nothing. The feature playbooks require it before handing off.

**A maintenance pass**, sweeping recent churn for surfaces the map never heard
of. That works, but it rediscovers from source what a feature run already knew,
and pays a full live sweep to do it. `open-world.md` arrived this way.
