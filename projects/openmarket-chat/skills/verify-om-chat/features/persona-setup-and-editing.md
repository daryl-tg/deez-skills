# Persona setup and editing

## Sub-features

- The Voice page as dense settings rows (since `417164da`): a **VOICE** section with **Edit** and **Try it** in its header, a "How your voice is used" chain (*Your messages → card → Away replies*), and the rows Persona, Learning, Rules, Boundaries, Examples and Voice cards.
- Global profile selection from the Persona row: the **Profile to load** combobox, **Load profile**, **Default voice** and **Add sample profiles**; a full-profile dialog from the Rules, Boundaries and Examples rows.
- Automatic learning (since `e7c375ce`): one global **Learn from my messages** switch and a **Learning details** dialog. Proposed changes, the learning hold with **Resume from reviewed voice**, and the per-profile "stays fixed" branch with **Allow learning into this profile** are gone (`02eb34ca` dropped their calls). A hold or proposal from an older daemon renders nothing.
- Immediate historical setup (**Set up my voice now**), resume, active progress with **Cancel setup**, insufficient history, and a proposed first card with **Use this card**.
- Manual creation (**Create**), structured edits (**Edit**), and import of a native selfmd pair or one folded Markdown file (**Import**); save is separate from selection.
- Evidence-free default export, optional private evidence; History and the advanced document from the **More voice card actions** menu.
- Hosted `/chat/` parity over Remote Control: every Voice and Away call runs on the owner's home daemon by operation name, with unreachable-desk states (offline, remote control off, outdated, busy, no answer). On origin/main since `2a737b9e`; end-to-end use still needs a relay and home daemon that speak the `operation` verb.
- The Library persona card labels `default_voice` ("Default voice"), `fold_pending` ("Adding your text"), `refused_scan`, `skill_conflict`, `skill_unavailable` and any unknown state ("Unknown status"). Only "Unknown status" is reachable on the fixture (see [your-library.md](your-library.md)); the others are unit-tested only.

## How to get to it (user POV)

Open Agents, then **Voice** in the sidebar's **Persona** group (a `nav` named "Persona sections"). The page reads **VOICE**. With no card, the Persona row offers **Set up** (accessible name **Set up my voice now**; **Resume setup** when a setup can resume), and the Voice cards row offers **Import** and **Create**. A proposed first card shows **Use this card** in the Persona row. With a card selected, press **Edit** to change it, **Try it** to hear it, and open **More** (**More voice card actions**) for Export, History and Advanced. Away coverage and Activity are the other two Persona rows; this surface does not arm an agent.

### Switching profiles

Profile selection lives in the Persona row; the **Saved profiles** disclosure is gone. **Profile to load** is a custom combobox, not a native select: open it by accessible name and pick the named `option`. Its options are **Default voice**, the saved profiles, and **Add sample profiles** (in a "Library" group). Picking a profile other than the loaded one reveals **Load profile** (visible "Load"); changing the picker alone does not change the loaded card. On `persona-panel-fixture.html`, pick **Brief** and press **Load profile**: the chain reads "Brief v2", "2 rules · 1 boundary", and the Persona row reads "Selected Brief". **Default voice** clears the selection (`selectedDocId` null).

Duplicate names include their paths in the picker. Importing a second card with the same managed skill name can fail to load; verify actionable rename guidance and that the prior selection and digest remain intact.

The full-profile dialog shows the complete readable card body, including advanced sections and code blocks. Check the last section against the API report, close with Escape and verify focus returns to the row button, then reopen and exercise **Close**. ### Hosted /chat/ over Remote Control (on origin/main since `2a737b9e`)

In the hosted app the Persona hub reaches the home daemon through the Remote Control `operation` verb, never daemon HTTP. Source: `packages/chat-ui/src/lib/remote-operation.ts` (`remoteOperation(name, init)`), its operator registry `lib/remote-operator-registry.ts`, the copy in `lib/remote-unavailable.ts`, `RemoteControl.operation()` in `remote-control.ts`, and the cloud adapters `apps/cloud/src/lib/{local-operation,away-client,daemon-operations,om-daemon}.ts`. The daemon maps the closed name list to its routes (`@openmarket/rooms-client/remote-operation-routes`, daemon-only). The cloud dist must never contain `/api/away` or `/api/library/` (`apps/cloud/tools/check-dist.mjs`).

Driving it needs a three-hop rig: a local relay from `kiyotaka-chat-service` (Redis off, dev RS256 `JWT_KEYS`), a `control-om` lane daemon with `OM_ROOMS_WS_URL` at that relay and remote control enabled, a local store (`tharamine-user-service` on a fresh `mongo:7` replica set) for Voice data, and the cloud app under `vite` on 4178 with an out-of-repo proxy config and seeded `jwt` + `om.chat.voucher` localStorage. Start vite with `--force` after any rooms-client link change: a stale dep pre-bundle makes the lazy Remote Control chunk fail and every call reads offline. Full runbook: the task's dev-notes `rig.md` (cloud-persona-parity).

**Fixture lane (no relay).** The `/chat/` shell fixture registers no remote operator, so every call answers 503 `remote_offline` and only the offline state renders. Open `/chat/tools/visual/shell-fixture.html?view=agents&alerts=quiet` on the cloud lane, then click `button` **Voice** in `nav` **Persona sections**. The path becomes `/chat/agents/voice` and the page reads "Your desk is offline. Voice settings load when om at your desk is running." **Away coverage, status can't tell right now** goes to `/chat/agents/away` and reads "Your desk is offline. Away coverage needs om running at your desk." `?view=agent&panel=voice` does not work there: the cloud fixture has no persona mock, and its sections route on the pathname (`apps/cloud/src/lib/routing.ts:342`). The other states (off, outdated, busy, no answer: `remote-unavailable.ts:23-41`) need a registered operator or the rig below.

Unreachable states to drive: stop the lane (Voice "Your desk is offline. Voice settings load when om at your desk is running.", Away "Your desk is offline. Away coverage needs om running at your desk.", sidebar Away "Can't tell"); `om agent remote disable` on the lane ("Remote control is off at your desk. Turn it on with om agent remote enable."). For `/rooms` regression set `OM_ROOMS_GUI_DIR` on the lane to the candidate `dist/` and confirm zero relay `operation` frames.

## Gotchas

The canned fixture proves navigation and component behavior. An actual HTTP handler with a synthetic relay adapter proves API integration, not deployed relay delivery. Setup with an injected zero-history learner does not prove a paid model pass. Test durable checkpoint reuse and publication separately in the daemon suite.

The report can legitimately contain text:null for no selected card. Treat it as an empty state, not an old daemon. A missing model must leave the editor usable. Learning may remain off after setup. Hand-edited empty rules must not revive stale embedded JSON. Never include private evidence in exported proof artifacts by default.

There is no cross-fork drift report: `sync-shared.ts` was deleted in `f190644c` and the persona UI is one shared implementation under `packages/chat-ui/src/`. A persona change is in `/rooms` and `/chat/` at once, so drive both hosts rather than looking for a twin to reconcile.

The actual API rig must include a synthetic HOME mirror-health entry and directory to prove managed voice skill publication. Missing mirror state should produce an unavailable load and preserve the previous selection; a 200 report by itself is not proof that the voice skill exists. Never configure that rig against the operator’s real mirror.
