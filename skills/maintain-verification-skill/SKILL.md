# Maintain a verification skill

A feature map rots the moment the app changes. This is the upkeep loop for a
skill generated by `create-verification-skill`. The unit of rigor is the
feature, not the sentence: cover every feature file from source, exercise every
feature live. Follow the canonical layout, ownership, and persistence contract
in [`../../docs/project-verification.md`](../../docs/project-verification.md).

## Outcomes

Pick one and say which.

- **clean** — every feature got source and live coverage, nothing worth
  shipping. No branch, no PR.
- **changed** — proven map corrections published; non-map hub corrections use
  their ordinary review path.
- **blocked** — coverage could not finish, or a proven fix could not ship
  safely. Say exactly what blocked it.

## Edit scope

Only the canonical project-owned verification skill directory in the deez-skills
hub and its tracked `bin/control-<app>` wrapper. **Never product code or a
project-local copy.** A behavior the map describes that the app no longer does
is either doc drift, which you fix, or a product regression, which you report.
Never paper over a regression in docs. Respect documented special-wrapper
ownership; in particular, OpenFloor's operator-only untracked wrapper is outside
scope and must never be reconstructed or replaced.

## Pass

**0. Locate the target.** Resolve the installed `verify-<app>` through its
registry project ownership first, or through its installed symlink when needed,
then map it back to
`~/github/deez-skills/projects/<repository>/skills/verify-<app>/`. The repository
name is the origin remote basename with `.git` stripped, never a feature-worktree
name. Do not default to a project-local `skills/verify-*` directory. Several
candidates, ask which. None, stop and point at `create-verification-skill`.

**1. Index hygiene.** Read the feature map README and glob its siblings. Fix
missing, extra, duplicate, or dead entries, including new feature files written
by Clanker. Every feature entry records its last verified date, the product
commit or tree driven, verification scope, and limitations.

**2. Source wave.** One read-only subagent per feature file, launched
concurrently, on the **explore** role. Each explains how that user-facing
feature works from source, flags likely doc drift with citations, and returns
one concise live-verification recipe. Children never drive the app and never
edit files.

**3. Reconcile.** Every feature file has a returned summary. Merge overlapping
recipes into as few app states as practical. Spot-check cited drift; do not
re-prove clean claims. Sweep recent churn for user-facing surfaces missing from
the map, requiring a concrete source path before calling one missing.

**4. Live pass.** Required even when source looks clean. You own all driving.
Follow the verification skill's own launch model. Exercise every feature at
least once, holding three invariants whatever fails:

1. **Never drive an instance you have not health-checked since it last did
   something surprising.** `control-<app> doctor` before the first drive, again
   after any failed drive. Where doctor cannot see the failure, such as a wedged
   UI on a healthy process, reset to a known state or relaunch rather than
   hoping.
2. **Evidence captured so far survives every cleanup**, checked at its named
   location, not assumed.
3. **Nothing a drive started outlives that drive's usefulness.** Clean
   failed-iteration residue whether the session is stuck, exited, or shared. For
   a shared instance clean the residue, not the instance.

A doctor failure caused by skill drift is drift: fix it under edit scope and
retry once before calling the pass blocked. A feature that cannot be reached is
`verified-unreachable` only with the concrete unmet prerequisite and the route
attempted; if the map omits that prerequisite, that is drift. Any harness fix
gets re-driven live before it ships. Final teardown happens after the last drive
including re-proofs, and evidence stays.

**5. Triage.** Wrong or missing user-POV description is doc drift, fix it.
Working behavior the harness cannot drive is a harness gap, fix it; scripts stay
executable with invocation documented. App behavior actually broken is a product
gap: record it for the operator, keep it out of this PR.

**6. Persist or stop.** For changed, re-read every changed file and follow the
shared project-verification contract. Once map changes are proved and the index
is current, automatically publish only the changed `features/*.md` files with
`bin/deez sync-feature-maps <project> <verify-skill> <map-file.md>...`. Pass
filenames relative to `features/`, including `README.md` when it changed. If no
map file changed, publish nothing. Never use bare `bin/sync`, and never include
`SKILL.md`, wrappers, registry/config files, raw evidence, or product repository
changes. All non-map source edits use their ordinary review and delivery path;
standing authorization to publish feature maps does not authorize a product
push. For clean or blocked, report the outcome and coverage honestly.

Keep concise run notes in a scratch location. Do not commit them.
