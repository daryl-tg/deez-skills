# Maintain a verification skill

A feature map rots the moment the app changes. This is the upkeep loop for a
skill generated by `create-verification-skill`. The unit of rigor is the
feature, not the sentence: discover the product's user-facing surfaces, reconcile
them with the map, and exercise their user paths live. Follow the canonical
layout, ownership, and persistence contract
in [`../../docs/project-verification.md`](../../docs/project-verification.md).
A formal check, such as a model or a proof harness, is kept in line by
**maintain-formal-verification-skill** instead.

## Outcomes

Pick one and say which.

- **clean** — the source inventory is reconciled, every feature got source and
  live coverage, no unresolved discovery gaps, and nothing remains to publish.
- **changed** — proven map corrections published; non-map hub corrections use
  their ordinary review path.
- **blocked** — coverage could not finish, or a proven fix could not ship
  safely. Say exactly what blocked it.

## Edit scope

Only the canonical project-owned verification skill directory in the deez-skills
hub and its tracked `bin/control-<app>` wrapper. **Never product code or a
project-local copy.** A behavior the map describes that the app no longer does
is either doc drift, which you fix, or a product regression, which you report.
Never paper over a regression in docs. Respect documented special-wrapper
ownership; in particular, OpenFloor's operator-only untracked wrapper is outside
scope and must never be reconstructed or replaced.

## Pass

**0. Locate the target.** Resolve the installed `verify-<app>` through its
registry project ownership first, or through its installed symlink when needed,
then map it back to
`~/github/deez-skills/projects/<repository>/skills/verify-<app>/`. The repository
name is the origin remote basename with `.git` stripped, never a feature-worktree
name. Do not default to a project-local `skills/verify-*` directory. Several
candidates, ask which. None, stop and point at `create-verification-skill`.
When the caller supplies an isolated hub worktree, resolve ownership from its
registry and edit its `projects/` directory. Do not follow installed symlinks
back into the operator's working checkout. Read the current fetched remote map;
a stale local map is not the discovery baseline.

**1. Discover and reconcile the inventory.** Start from the product source,
not the existing feature files. Enumerate applicable routes/navigation, screens,
CLI command registrations, public API/MCP actions, settings, and major workflows.
Use entry-point registries and their implementations; recent churn is an extra
input, never the discovery boundary. Group coherent user outcomes rather than
making a feature out of every component or endpoint.

Keep a `Surface inventory` table in `features/README.md`: user outcome, concrete
source path, matching guide/sub-feature or `unmapped`, live verification status,
and remaining prerequisite or gap. Record the product tree and discovery date.
Existing guides may cover several outcomes, but name the actual section/path.
Include older unchanged surfaces and source-supported surfaces blocked by auth,
data, flags, or a missing harness. Mark those `live verification pending`; source
inspection is not live proof. Keep unresolved rows across runs until proved,
mapped, or removed with source evidence. An incomplete inventory is a coverage
gap, not a clean pass. See the shared contract's discovery rules.

Read the feature map README and glob its siblings. Fix
missing, extra, duplicate, or dead entries, including new feature files written
by Clanker. Every feature entry records its last verified date, the product
commit or tree driven, verification scope, and limitations.

**2. Source wave.** Assign bounded read-only **explore** readers to the existing
guides and newly discovered gaps, batching independent work within the runtime's
agent limit. Each explains the user-facing behavior from source, cites likely
drift or missing coverage, and returns a concise live-verification recipe.
Children never drive the app and never edit files.

**3. Reconcile.** Every guide and inventory gap has a returned summary. Merge
overlapping recipes into as few app states as practical. Spot-check cited drift; do not
re-prove clean source claims. Plan live coverage for both mapped features and
new outcomes. Give each inventory row a guide or an explicit pending reason.

**4. Live pass.** Required even when source looks clean. You own all driving.
Follow the verification skill's own launch model. Exercise every mapped feature
and newly discovered reachable outcome at least once, holding three invariants
whatever fails:

1. **Never drive an instance you have not health-checked since it last did
   something surprising.** `control-<app> doctor` before the first drive, again
   after any failed drive. Where doctor cannot see the failure, such as a wedged
   UI on a healthy process, reset to a known state or relaunch rather than
   hoping.
2. **Evidence captured so far survives every cleanup**, checked at its named
   location, not assumed.
3. **Nothing a drive started outlives that drive's usefulness.** Clean
   failed-iteration residue whether the session is stuck, exited, or shared. For
   a shared instance clean the residue, not the instance.

A doctor failure caused by skill drift is drift: fix it under edit scope and
retry once before calling the pass blocked. A feature that cannot be reached
remains `live verification pending`, with the concrete unmet prerequisite and
route attempted recorded; if the map omits that prerequisite, that is drift. An
attempt proves the reachability limitation, not the feature. Any harness fix
gets re-driven live before it ships. Final teardown happens after the last drive
including re-proofs, and evidence stays.

**5. Triage.** Wrong or missing user-POV description is doc drift, fix it.
Working behavior the harness cannot drive is a harness gap, fix it; scripts stay
executable with invocation documented. App behavior actually broken is a product
gap: record it for the operator, keep it out of this PR.

**6. Persist and report.** Add a guide for each newly live-proved outcome, or
extend the matching guide when it belongs to an existing feature. Keep the
inventory, index, recipe, and provenance consistent. Unreachable or undriven
discoveries stay visible in the README with source evidence and pending status;
never invent a successful drive or discard them because this pass is blocked.

Re-read every changed file and follow the shared project-verification contract.
The operator's deez-skills map-only exception permits these commits and pushes
under a general workflow push restriction. Honor `.sync-hold` and newer explicit
requests to pause map publication.
Publish independently proved map corrections and source-supported inventory
updates even when another feature leaves the overall pass blocked. A pending
row does not claim live verification. Automatically publish only the changed
`features/*.md` files with
`bin/deez sync-feature-maps <project> <verify-skill> <map-file.md>...`. Pass
filenames relative to `features/`, including `README.md` when it changed. If no
map file changed, publish nothing. Never use bare `bin/sync`, and never include
`SKILL.md`, wrappers, registry/config files, raw evidence, or product repository
changes. All non-map source edits use their ordinary review and delivery path;
standing authorization to publish feature maps does not authorize a product
push. A refused push or `.sync-hold` is unsynced work, never published or clean.

Report inventory outcomes, mapped coverage, newly discovered and newly verified
outcomes, remaining gaps, changed map paths, map commit and push result. Repeated
verification stamps alone do not establish wider product coverage. Distinguish
source discovery, live proof, and remote publication in the run notes.

Keep concise run notes in a scratch location. Do not commit them.
